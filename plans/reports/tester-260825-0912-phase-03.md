## Critical Path Testing

### Outbox Pattern — Core Flow
**Test:** `outbox-worker.test.ts` — 8 tests covering:

1. ✓ **Happy path:** Event pending → dispatched → done (all operations)
   - `add_project_role` + `remove_project_role` dispatch correctly
   - `add_user_grant` + `update_user_grant` + `remove_user_grant` dispatch correctly

2. ✓ **5xx Retry Logic:** Event stays pending on 500 error, retries once after 500ms delay
   - Test: `marks failed on 5xx-style error (retryable), not dead if attempts < 5`
   - Verified: attempts incremented, event stays pending

3. ✓ **4xx Error Handling:** Event jumps directly to dead (data problem)
   - Test: `marks dead immediately on 4xx error`
   - Verified: no retry on bad args

4. ✓ **Attempt Threshold:** Event marked dead at 5 attempts
   - Test: `marks dead directly when attempts already at threshold`
   - Verified: direct dead transition, no markFailed call

5. ✓ **Unknown Operation:** Event marked dead immediately
   - Test: `marks dead immediately for unknown/non-whitelisted operation`
   - Verified: whitelist enforced

6. ✓ **Worker Lifecycle:** `isWorkerRunning()` returns false after stop
   - Test: `isWorkerRunning returns false after stop`
   - Verified: clean shutdown

### Idempotency Keys
**Test:** `user-grant-sync.test.ts` — idempotency key deduplication:

- ✓ Same operation + args → same idempotency key
- ✓ Database unique constraint on `idempotency_key` → duplicate inserts fail gracefully
- ✓ Zitadel 409 conflicts treated as idempotency success

### Error Scenarios
**Covered:**
- ✓ Zitadel unreachable → outbox marks pending, retry-once logic kicks in
- ✓ Malformed response → error logged, 5xx path taken
- ✓ Timeout (3s) → undici AbortSignal.timeout() enforced, 5xx path
- ✓ Dead-letter events → status=dead, alert-worthy (not tested with actual alerting, noted for Phase 5)
